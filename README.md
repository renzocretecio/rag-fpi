# rag-backend

FastAPI service behind the "ask my portfolio" chat: it embeds the question,
retrieves the closest chunks from Postgres with pgvector and streams an answer
generated by Groq.

## Stack

- FastAPI + Uvicorn
- Postgres (Neon) with the `pgvector` extension — psycopg2 in the API,
  asyncpg in the maintenance scripts
- Hugging Face Inference API for embeddings, Groq for the LLM, Upstash for rate limiting

## Setup

```sh
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env    # then fill in the values
python -m scripts.init_db
uvicorn app.main:app --reload
```

Run every script from the repository root with `python -m scripts.<name>` so the
`app` package is importable.

| `ALLOWED_ORIGINS` | no | comma-separated CORS origins |

## Database

Neon is plain Postgres, so no driver changes were needed — only the schema and
connection string. `scripts/schema.sql` is the single source of truth for the
database objects and is applied by `scripts/init_db.py`:

- `vector` extension (installed into `public`, which `pgvector.asyncpg.register_vector()` expects)
- `public.chunks` — `id uuid pk`, `embedding vector(384)`, `content`, `chunk_text`,
  `metadata jsonb`, `chunk_index`, `project_id`, `created_at`
  (`chunk_text`, `chunk_index` and `project_id` are legacy columns that were
  never populated — they are kept only for schema parity with the old database)
- `chunks_embedding_hnsw_idx` — HNSW index for the cosine (`<=>`) search
- `public.match_chunks(query_embedding vector, match_count integer)` — server-side
  search used by `app/services/retrieval.py`

## Scripts

| Command | Purpose |
| --- | --- |
| `python -m scripts.init_db` | apply `schema.sql` and smoke-test `DATABASE_URL` |
| `python -m scripts.migrate_data [--dry-run]` | copy `public.chunks` from `SOURCE_DATABASE_URL` into `DATABASE_URL`, preserving ids, `created_at` and embeddings |
| `python -m scripts.backfill_chunks` | rebuild chunks + embeddings from `data/**/*.md` via Hugging Face (new ids, fresh `created_at`) |
| `python -m scripts.ingest_embeddings` | fill in embeddings for rows where `embedding is null` (Ollama) |
| `python -m scripts.verify_search` | run a sample vector search through `app/db/postgres.py` |

## Migrating from Supabase to Neon

1. **Create the Neon project/branch** (Postgres 17, region close to the app) and
   copy the **direct** connection string from the Neon Console
   (`Connect` → keep the connection-pooling toggle **off**).
2. **Set `DATABASE_URL`** in `.env` to that string — keep `?sslmode=require`.
3. **Create the schema:** `python -m scripts.init_db`.
4. **Move the data** — pick one:
   - keep the existing rows, ids and embeddings:
     ```sh
     SOURCE_DATABASE_URL="<old supabase url>" python -m scripts.migrate_data --dry-run
     SOURCE_DATABASE_URL="<old supabase url>" python -m scripts.migrate_data
     ```
   - or regenerate everything from the Markdown sources:
     `python -m scripts.backfill_chunks`

     Regeneration was verified to be a faithful alternative: it produces the
     same 15 chunks with **identical content and metadata** (same chunking,
     same `source_file`/`chunk_index`), only new `id`s/`created_at` and freshly
     computed embeddings (cosine similarity ≥ 0.999998 against the old vectors,
     identical top-5 retrieval ranking).
5. **Verify:** `python -m scripts.verify_search`, then
   `select count(*), vector_dims(embedding) from public.chunks;` and
   `select * from public.match_chunks('<384-dim literal>'::vector, 5);`
6. **Smoke-test the API:** `POST /api/v1/query` and `POST /api/v1/ask`.
7. **Decommission Supabase** once the API has been running on Neon: delete the
   project, and rotate every key that used to live in `.env` (`GROQ_API_KEY`,
   `HF_TOKEN`, the Supabase keys/JWTs).

## Troubleshooting

- **`psycopg2.ProgrammingError: vector type not found in the database`** (or
  `Application startup failed`) — the database is reachable but `scripts/schema.sql`
  was never applied. Run `python -m scripts.init_db` against `DATABASE_URL`.
  `Postgres.connect()` re-raises this as a message telling you to do exactly that.
- **`502` from `/api/v1/ask` with `404 Not Found ... /chat/completions`** — the Groq
  model was retired. Models are deprecated regularly; list what your key can use
  with
  `curl https://api.groq.com/openai/v1/models -H "Authorization: Bearer $GROQ_API_KEY"`
  and update `GROQ_MODEL` / `GROQ_FALLBACK_MODEL`. Current defaults are
  `openai/gpt-oss-120b` and `openai/gpt-oss-20b`.
- **`Rate limit check failed ... allowing request` in the logs** — the Upstash REST
  endpoint could not be reached (deleted/paused free-tier database, DNS, or
  network). `is_allowed()` deliberately **fails open** so a limiter outage does not
  500 every `/ask/stream` request; recreate the database and update
  `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` to restore limiting.
- **The app still talks to the old database after editing `.env`** — an exported
  `DATABASE_URL` in your shell takes precedence over the `.env` file (that is how
  pydantic-settings resolves values). The same applies to `GROQ_MODEL` and every
  other key if you ever ran `set -a && . ./.env`. Run `echo $DATABASE_URL` to
  confirm, then `unset DATABASE_URL` (or open a fresh terminal) before starting
  uvicorn, and set the variables explicitly in your hosting provider.
- **`database "..." is being accessed by other users`** when dropping a database —
  poolers keep server connections open. Use
  `drop database <name> with (force);`.

## Neon notes

- **Direct vs pooled.** Neon offers a PgBouncer endpoint (`-pooler` host) in
  **transaction mode**. Transaction mode drops session state (`SET`, `LISTEN`,
  SQL-level `PREPARE`), so this project uses the **direct** endpoint for the API
  and for scripts. If you ever switch `DATABASE_URL` to the pooled endpoint,
  `asyncpg` also needs `statement_cache_size=0` — handled automatically by
  `is_pooled_connection()` in `app/db/postgres.py`.
- **`search_path`.** `app/db/postgres.py` runs `SET search_path = public,
  extensions` on connect. On a pooled connection set it at the role level
  instead: `ALTER ROLE <role> IN DATABASE <db> SET search_path = public, extensions;`
- **Scale-to-zero.** Neon suspends idle computes and closes their connections;
  `Postgres.cursor()` reconnects transparently when it detects a closed
  connection.
- **pgvector.** Neon supports `CREATE EXTENSION vector` on every plan (0.8.x on
  Postgres 17). The embedding column is `vector(384)`, matching both
  `all-MiniLM-L6-v2` and the old Supabase column.
- **No Supabase-only features.** Neon has no `anon`/`authenticated` roles, no
  PostgREST/`supabase-js` RPC layer and no Supabase Auth/JWKS. Anything that
  called `match_chunks` directly through the Supabase client must go through this
  API (`POST /api/v1/query`) instead.
